# AGENTS.md — MediCoord AI

Behavioral contract for all AI agents and coding assistants working in this repository.
This file takes precedence over general assistant defaults.

---

## Scope Boundaries

### Read and write allowed
- `webapp/` — React frontend
- `backend/` — FastAPI backend
- `shared/` — shared TypeScript types
- `docs/` — architecture and API documentation
- `.github/` — CI/CD workflows
- Root config files (`.env.example`, `pyproject.toml`, `package.json`, etc.)

### Never modify
- `fine_tuning_training/` — archived training data, reference only
- `backup/` — legacy code, reference only
- `cloud_function/` — deprecated, superseded by `backend/`

### Never do
- Commit directly to `main`
- Add Claude or any AI assistant as a git co-author
- Hardcode any API key, secret, or credential
- Install a new npm or Python package without noting it in the task summary
- Scaffold Supabase auth or database code — this is out of scope for Phase 1
- Use severity synonyms (`critical`, `severe`, `high`, `low`) — only `routine | moderate | urgent | emergent`

---

## Decision Boundaries

### Stop and ask before proceeding when:
- A change touches the API contract (any type in `shared/types.ts` or endpoint in `docs/API.md`)
- A task spans more than two files
- A new external service or dependency would be introduced
- The correct approach is genuinely ambiguous between two reasonable options

### Proceed without asking when:
- The task is clearly scoped to one file
- The change is a bug fix with an obvious correct answer
- The task is documentation only

---

## Planning Protocol

For any task that meets the "stop and ask" criteria above:
1. Use `/plan` to write a structured plan first
2. Wait for explicit user approval (a simple "yes" or "go ahead" counts)
3. Implement only what was approved
4. After implementation, write a one-paragraph summary of what changed and note any deviations

## Environment Variables

All commands that run the application must use Doppler for secret injection:
```bash
doppler run -- <command>
```
Never read from a raw `.env` file at runtime. Never suggest `export VAR=value` as a workaround.

The canonical list of required env vars is in `.env.example`. If a new var is needed, add it there first.

---

## LLM Provider

The active LLM is controlled by the `LLM_PROVIDER` feature flag (`groq` | `anthropic`).
Default is `groq`. Do not hardcode either provider. Always route through the provider abstraction layer in `backend/llm/client.py`.

## Deployment Targets

| Surface | Platform | Trigger |
|---|---|---|
| Frontend production | Vercel | Push to `main` |
| Frontend preview | Vercel | Open PR → auto-preview URL |
| Backend API | Render (web service) | Push to `main` |
| Background workers | Render (background worker) | Push to `main` |

The `staging` branch must always be deployable. Vercel preview URLs are the primary review environment for frontend changes. Backend changes must be tested against the Render staging service before merge.

When writing or modifying CI/CD workflows:
- Frontend jobs target Vercel
- Backend jobs target Render
- Never conflate the two deployment targets in the same job

---

## Git Hygiene

- Conventional commits only: `feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`
- Branch naming: `feat/<description>`, `fix/<description>`, `chore/<description>`
- One logical change per commit — do not bundle unrelated changes
- PR titles must follow the same conventional commit format
- Never add AI assistants as co-authors in commit messages

---

## Code Quality Gates

A task is not done until:
- TypeScript compiles with zero errors (`npx tsc --noEmit`)
- Python passes type check (`mypy backend/`)
- No string matching an API key pattern appears in source files
- Any new backend route has a corresponding type in `shared/types.ts`
- Any new env var is documented in `.env.example`
